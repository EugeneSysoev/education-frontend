# Hacker News exercise

## Источник задачи

- [Задание ментора «10 Hacker News»](https://teal-produce-2f9.notion.site/10-Hacker-News-25e1f21638f581578d1ce1fd16d14d2b)
- [React Practice — Show top 10 articles from Hacker News](https://reactpractice.dev/exercise/show-top-10-articles-from-hacker-news/)
- [Официальная документация Hacker News API](https://github.com/HackerNews/API)

## Цель

Отработать загрузку связанных данных из нескольких endpoint: сначала получить
ранжированный список идентификаторов, затем параллельно запросить детали первых
десяти элементов и показать только целостный результат.

## Функциональные требования

Создайте React-компонент со списком десяти верхних публикаций Hacker News.

1. Получите идентификаторы через официальный endpoint Top Stories.
2. Выберите первые десять идентификаторов в полученном порядке.
3. Для каждого идентификатора загрузите отдельный item.
4. Покажите score, title, URL и author каждой публикации.
5. Не показывайте детали публикаций, пока не завершилась вся группа загрузок.
6. Представьте loading, error, empty и success как взаимоисключающие состояния.

## Теория перед кодом

API задаёт двухэтапный граф:

```text
GET /v0/topstories.json
          ↓
    первые 10 id
          ↓
GET /v0/item/<id>.json × 10
          ↓
   полный список статей
```

Первый и второй этапы зависимы: без списка `id` невозможно построить URL
деталей. Запросы отдельных публикаций, напротив, независимы. Их
последовательное ожидание увеличивает общее время до суммы задержек, тогда как
параллельный запуск приближает его к самой медленной операции группы.

Порядок ответа сети и порядок отображения — разные понятия. Более поздний
запрос может завершиться первым, но итоговый список должен сохранить рейтинг
из `topstories`. По условию частичные данные не показываются, поэтому до
завершения группы интерфейс остаётся в loading-состоянии.

Ответ API является runtime-данными. Тип TypeScript не превращает неизвестный
JSON в достоверную статью. Проверять нужно минимальную форму, необходимую
интерфейсу, и отдельно определить политику для отсутствующего `url`, удалённого
item и ошибки одного из запросов.

## Перед кодом

Ответьте своими словами:

1. Почему нельзя получить все нужные поля одним запросом `topstories`?
2. Где проходит граница между последовательными и параллельными этапами?
3. Почему `await` внутри обычного цикла может создать waterfall?
4. Как сохранить исходный порядок при разном времени ответов?
5. Чем сетевая ошибка отличается от HTTP-ответа с ошибочным статусом?
6. Должен ли один неуспешный item разрешать показать девять остальных, если
   условие требует дождаться всех данных?
7. Какие поля нужны компоненту и какие из них API может не прислать?
8. Что должно произойти с незавершёнными запросами при размонтировании?

Сначала покажите ответы и схему состояний на review. До этого не пишите JSX,
`fetch`, query и готовые обработчики.

## Проверка

```bash
npm run build:sandbox
npm run lint
```

Ручные сценарии: успешная загрузка десяти публикаций, медленный ответ одной
детали, ошибка списка идентификаторов, ошибка одного item, неожиданный JSON,
отсутствующий URL, пустой результат и размонтирование во время загрузки.
