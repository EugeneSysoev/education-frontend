## Учебная цель

Разобрать двухэтапную загрузку связанных данных: сначала получить ранжированный
массив идентификаторов, затем загрузить сведения о первых десяти публикациях.
Основные темы: граф запросов, параллельность, порядок результатов, атомарное
состояние интерфейса, runtime-граница внешнего JSON и обработка ошибок.

## Теория до решения

До кода нужно разобрать пять частей задачи.

### 1. Контракт API

Endpoint `topstories` возвращает не статьи, а упорядоченный массив числовых
идентификаторов. Сведения об одной публикации запрашиваются отдельно по её
`id`. Значит, интерфейс строится не по результату одного запроса, а по графу
`1 + 10` запросов.

### 2. Последовательность и параллельность

Второй этап нельзя начать до получения идентификаторов. Но после выбора первых
десяти их детали независимы и не должны загружаться по одной цепочкой. Нужно
объяснить разницу между зависимыми этапами и параллельными операциями внутри
второго этапа, не записывая готовую реализацию.

### 3. Единый результат

По условию детали статей не показываются, пока не загружены все десять. Поэтому
частично заполненный список не является состоянием успеха. До кода нужно решить,
что увидит пользователь во время общей загрузки и что произойдёт, если один из
запросов деталей завершится ошибкой.

### 4. Недоверенная граница

TypeScript описывает ожидания программы, но не проверяет JSON во время
выполнения. Для карточки нужны только `id`, `score`, `title`, `url` и `by`.
Официальный API допускает отсутствие некоторых полей, поэтому отдельно нужно
определить поведение для публикации без внешнего `url`, удалённого или
неожиданного элемента.

### 5. Жизненный цикл запроса

Нужно различать React state и внешний процесс загрузки. Повторный рендер сам по
себе не должен запускать новый набор запросов. Также заранее определяется, как
не допустить обновление состояния после размонтирования компонента.

## Первый конкретный шаг

Не писать JSX и `fetch`. Сначала нарисовать поток данных:

```text
topstories → список id → первые 10 id → 10 запросов деталей → единый результат
```

Затем своими словами ответить:

1. Почему задача требует двух этапов запросов?
2. Какие операции обязаны идти последовательно, а какие можно выполнять
   параллельно?
3. Почему последовательный `await` десяти независимых запросов создаёт
   waterfall?
4. Сохраняется ли исходный порядок идентификаторов, если ответы приходят в
   разное время?
5. Какие состояния интерфейса нужны до появления полного списка?
6. Что должно произойти при HTTP-ошибке одного запроса деталей?
7. Какие поля JSON являются минимально необходимыми и как относиться к
   отсутствующему `url`?
8. Что должно остановить или обезвредить незавершённую загрузку при
   размонтировании?

Только после review ответов разрешается предложить TypeScript-типы, сигнатуры
функций data layer и способ управления server state.

## Этапы review

1. Схема запросов, состояния интерфейса и политика ошибок без кода.
2. Минимальные типы и runtime-проверка ответа API.
3. Функции data layer без JSX.
4. Параллельная загрузка деталей с сохранением рейтингового порядка.
5. Подключение к React и взаимоисключающие loading/error/empty/success.
6. Ручные сценарии, build и lint.

## Критерии завершения

- Использован официальный Hacker News Top Stories API.
- Загружаются детали первых десяти идентификаторов.
- Для статьи отображаются score, title, URL и author.
- Детали списка не показываются до завершения всей группы запросов.
- Независимые запросы деталей не образуют последовательный waterfall.
- Рейтинговый порядок из `topstories` сохраняется.
- HTTP-ошибки и неожиданный JSON обрабатываются явно.
- Loading, error, empty и success не противоречат друг другу.
- Нет `any` и необоснованных type assertions `as`.
- `npm run build:sandbox` и `npm run lint` проходят.
