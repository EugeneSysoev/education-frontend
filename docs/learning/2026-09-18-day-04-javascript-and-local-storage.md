## Следующая React-задача: `useLocalStorage`

В [React Practice Calendar](https://reactpractice.dev/start-here/) после
Holidays App идёт Accordion, который уже выполнен в День 2. Следующее
невыполненное упражнение по порядку —
[custom hook для localStorage](https://reactpractice.dev/exercise/create-a-custom-hook-that-allows-saving-items-to-the-local-storage/).

Стартовый Todo уже умеет добавлять и удалять задачи, но после перезагрузки
страницы список сбрасывается. Нужно вынести синхронизацию с `localStorage` в
переиспользуемый generic-хук `useLocalStorage<T>` и подключить его вместо
обычного `useState` для списка задач.

### Первый шаг

Открыть `react-lab/src/exercises/use-local-storage/README.md` и до кода ответить:

1. Откуда берётся начальное значение списка?
2. Почему чтение нужно передать в `useState` как lazy initializer?
3. Какая операция синхронизирует React state с внешней системой?
4. От каких значений зависит эффект записи?

Затем создать только сигнатуру `useLocalStorage<T>(key, initialValue)` и
псевдокод чтения/записи. Реализацию начинать после review плана.

Критерий первого шага: ученик своими словами разделяет инициализацию state и
последующую синхронизацию с `localStorage`.

### Практика

1. Один раз прочитать значение из `localStorage` при инициализации state.
2. При отсутствии ключа использовать `initialValue`.
3. При ошибочном JSON не ронять приложение: вернуть `initialValue` и вывести
   понятное диагностическое сообщение.
4. После изменения state сериализовать новое значение в `localStorage`.
5. Подключить хук к списку Todo и вручную проверить сохранение после reload.

### Критерии завершения

- Логика чтения и записи находится в custom hook, а не в `TodoApp`.
- Нет `any` и type assertions `as`.
- Хук поддерживает строки, числа, boolean, массивы и объекты через generic `T`.
- Значение переживает перезагрузку страницы.
- Отсутствующий ключ и повреждённый JSON обработаны явно.
- `npm run build:sandbox` и `npm run lint` проходят в `react-lab`.
- Ученик объясняет lazy initializer, зависимости эффекта и поведение при смене
  `key`.

- Результат: создан generic-хук `useLocalStorage<T>`. Чтение выполняется через

  в локальном браузере; удаление ранее проверено учеником. Повреждённый JSON
  приводит к диагностике в консоли и безопасному восстановлению
  `initialTodos`, приложение продолжает работать. В `StrictMode` диагностика
  появляется дважды, потому что React повторно вызывает initializer в
  development-режиме.
- Автоматические проверки 1 октября: `npm run build:sandbox` — успешно;
  `npm run lint` — успешно; `npm run test:practice` — 11/11;
  `npm test` — 8/8. Автоматических тестов для самого хука в проекте нет.
- Что получилось самостоятельно: после разбора потока данных ученик
  последовательно реализовал lazy initialization, обработку fallback,
  синхронизацию через эффект и интеграцию с Todo.
- Где потребовалась помощь: декомпозиция чтения и записи, отличие setter от
  сохраняемого значения, зависимости эффекта, generic `T`, типы
  `Dispatch<SetStateAction<T>>`, подключение хука к компоненту и замена
  устаревшего `FormEvent` на `SubmitEvent`.
- Ошибки и их причины: первая версия читала `localStorage` при каждом рендере,
  передавала `null` в `JSON.parse`, заменяла falsy-значения через `||`, не
  возвращала fallback из `catch` и пыталась сериализовать updater-функцию до
  вычисления нового state. Причина — смешение этапов инициализации, обновления
  React state и синхронизации внешней системы.
- Что ученик объяснил своими словами: выбор сохранённого значения или
  `initialValue`, роль React state как источника истины после инициализации,
  необходимость иммутабельного массива и разделение ответственности между
  `TodoApp` и custom hook.
- Что повторить: различие новой ссылки и функционального setter, runtime-границу
  `JSON.parse`, поведение хука при смене `key` и точное определение зависимостей
  эффекта.
- Поведение при смене `key`: lazy initializer не запускается повторно, поэтому
  текущий state сохраняется, а эффект записывает его уже под новым ключом. В
  этом упражнении ключ считается стабильным; чтение другого ключа при его смене
  потребовало бы отдельного контракта синхронизации.
- Финальный review: type assertion удалён, явный tuple-тип сохранён; текст
  интерфейса соответствует фактическому поведению.
